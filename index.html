How far are we from a lifelong game agent?

Evidence from a self-programming agent on ten browser games

Hao Chen · haochen2115@gmail.com · github.com/haochen2115

Model: DeepSeek V4.1 Flash (screenshots only) Environment: GameWorld browser games 4,743 attempts · 1.16M environment steps API cost $313 · no GPU

Abstract

A lifelong game agent should learn any new game from feedback alone, and should learn each new game faster than the last. We test how far current models are from this goal with an agent that never updates its weights. It keeps a persistent workspace in which it writes its own skill programs, notes and scoreboards. Every game receives the same prompts, with no per-game human engineering.

Across ten browser games and roughly 4,700 attempts we find the following. The agent learns within a single game, but only when it writes its experience as executable code. Given no memory structure at all, it invents the structures that within-game learning needs. What it learns, however, barely travels. The benefit of prior games is a constant that does not grow with experience, and experience from games of the same genre gives no extra benefit. A ladder of increasingly large changes shows that experience helps only while the screen looks the same: inverting the colours of an otherwise identical game turns experience from an asset into a liability. When the agent learns a chain of games in sequence, it neither learns faster over time nor keeps what it learned, because new code written for one game breaks the skills of another.

Within-game self-improvement and self-organised memory are within reach today. The main gap on the way to a lifelong game agent is that the agent's experience is anchored to pixels: it lacks a representation that is independent of what the screen looks like.

1Introduction

Experienced human players have an ability that is rarely measured. Given a game they have never seen, they become competent within a few rounds, and they get faster at this the more games they have played. We call a system with this ability a lifelong game agent. It needs at least three capabilities:

  • Improve within a game from the game's own feedback, not from rules a human wrote for it.
  • Organise its own memory: decide what to keep and how, without a human designing data structures for each game.
  • Carry experience forward: the cost of learning the N-th game falls as N grows, and games already learned are not forgotten.

Large models make it possible to try this without training any weights. A vision-language model can read a screen, write code and reflect on failure. Give it a workspace it can read and rewrite across attempts, and in principle it can bank each lesson and reuse it on the next game. Prior work has done versions of this inside a single world such as Minecraft (Voyager, Cradle and others), but mostly through structured game interfaces, and without measuring transfer between different games against agents that start from scratch.

This report uses a deliberately simple and general agent to ask: by the three criteria above, how far are we from a lifelong game agent today? Our contributions are:

  1. An evaluation protocol with zero per-game engineering: single-game learning, cross-game sequences, a similarity ladder, and a continual-learning performance matrix, each paired with a from-scratch control.
  2. Six empirical findings covering the three capabilities, each backed by mechanistic evidence from the code and notes the agent wrote.
  3. A diagnosis of the gap: experience stops helping as soon as the screen changes, because the agent stores it in pixel coordinates.

2Environment and metrics

We use the GameWorld suite of browser games. At every step the agent sees one screenshot and chooses one of a handful of key actions registered for the game. The game is paused while the model thinks, so inference speed does not affect play. An attempt is 400 steps, and each action lasts 0.1 to 0.2 seconds. We selected ten games that score reliably and differ in how they are played, and grouped them into four genres:

Task progress. Each game has a task goal. GameWorld computes progress toward it from the game's internal state, on a scale from 0 to 1, where 1 means the goal is met. The agent never sees this number, only the score shown on screen. Random play is not near zero: it averages 0.40 over all scoreable tasks, so every number in this report should be read against the random level.

Hidden seeds. The agent learns on one set of random seeds. Final performance is measured on a separate set it has never seen, with learning switched off.

Environment fixes. In 31 of GameWorld's 165 tasks, the scoring rule refers to a field the game never emits, so every policy scores 0. We mapped these fields to the equivalent fields the games do emit, and log the mapping with every run.

3The agent: a player that programs itself

The agent's entire state is a directory that it reads and writes itself; no human edits it. The directory holds four things: cross-game notes, per-game notes, a shared code library that any game's skill can import, and, for every game, all versions of its skill program with a scoreboard for each.

Three design constraints hold throughout. First, feedback is limited to what a human player sees: the on-screen score and deaths. The task-progress metric is hidden from the agent. Second, no per-game engineering: every game gets identical prompts. Third, we never prescribe the content of memory. We may change when the agent reflects, what it can see and how much it may store, but we never tell it what to remember. If it does not discover game rules on its own, that is itself a result.

For comparison we also ran random play; a memoryless agent (a newcomer every attempt, with the model choosing every action); two forms of text memory (the full history of all attempts in context, or a compact note rewritten after each attempt); and two forms of code memory (the fixed layout above, and a variant in which only the entry program play.py is specified and the agent organises everything else).

4Results

We report six findings in the order of the three capabilities. The first two concern improving within a game and organising memory; the last four concern carrying experience forward.

4.1Within a game, only experience written as code produces improvement

When the agent plays a single game for 10 attempts, both forms of text memory are indistinguishable from no memory and close to random play. Both forms of code memory raise task progress to 0.53 and 0.61; at that point 83% to 92% of all steps are decided by programs the agent wrote. Remove the programs and performance returns to where it started.

The reason is straightforward. Knowledge in a timing game is "how far is the obstacle, how fast is it moving, when should I press". It is only useful as a program that runs on every frame; written as a note, the model still needs a second per step to read the screen, and the moment has passed. The one exception confirms this. In Wolf3D, a compact text note reaches 0.83, because the game is about finding enemies, finding doors and exploring. These are decisions rather than reflexes, and text can carry them.

Below is the core of the skill the agent wrote for Chrome Dino. Over the next five attempts of 400 steps it did not call the model once, and each attempt cost about two cents:

# Chrome Dino skill written by the agent (excerpt; 131 lines in total)
gray = _gray(frame)
dark = gray < 118                      # dark pixels = dinosaur, cacti, ground
ground = _ground_row(dark, W, H)         # find the ground line
...
d = prev - obs_l                         # obstacle shift between frames = speed
spd = d if spd is None else 0.6 * spd + 0.4 * d
dist = obs_l - dino[1]
thr = 2.2 * spd                          # jump lead grows with speed
if dist <= thr:
    return "jump"

The code holds two kinds of knowledge at once: a threshold tied to how the screen looks (red: "pixels darker than 118 are objects") and a rule of the game that does not depend on the screen (blue: "jump earlier the faster things move"). Sections 4.4 and 4.5 show that this entanglement determines how far experience can travel.

4.2Given no memory structure, the agent builds what within-game learning needs

We ran 14 agents whose only convention was the entry program play.py, with no structure for notes, a library or a scoreboard. All 14 created notes; 13 rewrote their own program so that it writes a run log during play for the next reflection to read; 8 kept a score ledger. Self-written run logs were not part of the fixed layout we designed. These agents performed no worse than the fixed layout (0.61 against 0.53).

What did not appear matters as much. No agent built a library of rules reusable across games, a map, or a list of hypotheses to test. Within a single game the model already closes the engineering loop of recording, evaluating and rolling back on its own. A carrier of knowledge across games would need a different pressure or a different capability.

4.3The cross-game benefit is constant, and similar games give no extra benefit

We had agents play six games in a row and paired each game with an agent that started that game from scratch. We measure transfer with the learning-efficiency ratio TS(N): on the N-th game, the experienced agent's mean task progress over 10 attempts divided by that of the fresh agent. If the agent learns faster over time, TS(N) should rise with N.

Experience helps a little, but the advantage is the same on the second game as on the sixth; it does not accumulate. More surprisingly, experience from similar games gives no extra benefit. With the fixed layout, an agent that had played only similar games scored 0.12 below a fresh agent, and its first attempt was worse too (0.33 against 0.42). We tried three mechanism changes that do not prescribe content: running an "inherited" and a "from scratch" skill side by side in the first attempt of each new game and showing the agent both scores; capping total memory so the agent must choose what to keep; and removing all structure. None changed this result.

4.4Why: what it remembers across games is almost entirely engineering

Figure 4(a) gives the direct reason. Of the 66 cross-game bullets, about 40 are debugging and engineering practice, about 21 are image-processing tools, and only 5 are rules of a game. Three bullets from one agent's cross-game notes, in its own words (lightly abridged):

"Change one lever per attempt; keep the proven path bit-identical; revert if worse."
"A syntax or import error makes the whole skill dead. '0% skill decided' is a red flag."
"In a scrolling game, the number of steps a fixed-width object stays in the danger zone is width divided by speed."

The first two help the agent debug faster in any game. It did carry them to the next game, which probably explains the median TS of 1.27; they are complete after one or two games, so the benefit stops growing. The third is a genuine game rule, and exactly the rule that Chrome Dino and Geodash share. But it stayed in the notes and never became reusable code. On every new game the agent wrote a fresh perception-plus-decision program like the one in Section 4.1.

The code also explains why similar games hurt. On Chrome Dino the agent wrote a module that finds the ground and obstacles and put it in the shared library. On Geodash it imported that module to write its first skill, which scored 0.30 on the first attempt; a fresh agent that let the model read the screen scored 0.49. What it inherited was perception code, and perception is exactly where the two games differ most.

4.5Experience reaches only as far as the screen stays the same

If different games are too far apart, how small a change can experience survive? We built a ladder of increasingly large changes to the same game. We compared an experienced agent, whose workspace from 10 attempts on the original game was copied over unchanged, with a fresh agent, over 6 attempts each. The rungs were: the same game with a new seed; a change in control feel (key hold duration or game speed × 1.5); one changed rule (for example, enemies in Wolf3D have three times the health); and a reskin (the screenshot's colours are inverted and the channels rotated, game logic unchanged, and the written rules withheld). Three games and two seeds gave 87 agents in total.

The ladder draws a clear line. On the three rungs where the screen is unchanged, experience raises the first attempt by 0.01 to 0.13 and the six-attempt average by 0.10 to 0.17. After six attempts, though, the fresh agent catches up, and on hidden seeds the experienced agent no longer leads. Experience buys a faster start, not a higher ceiling. The scoreboards reveal a side effect: experienced agents switched back to their "proven champion" version in 81 of 108 attempts, fresh agents in 18. Experience made the agent explore less.

Once the screen changes, experience turns from an asset into a liability. After the reskin the experienced agent's first attempt scored 0.18 against the fresh agent's 0.45, and 5 of 6 pairs were negative. Its own revision notes tell the story. First it switched back to "champion v2"; then it wrote that "v2's fixed dark-mask (gray<118) selects the black background on the now-dark-mode page, so no jumps are ever emitted"; only on the third attempt did it produce a mask that works in both light and dark renderings. The perception code it stored, and its record of which version was the champion, both broke at once.

The one kind of experience that survived change was about decisions. When enemies in Wolf3D had three times the health, the experienced agent's first attempt was still 0.42 higher, because it had stored the map, the doors and a route for clearing enemies, all of which remained valid. One more observation: when Chrome Dino was changed so that points accrue only while ducking, none of 12 agents, over 72 attempts, systematically tried ducking. The agent does not explore to discover that the rules have changed.

Placing the ladder and Section 4.3 on one chart (Figure 7a), the value of experience falls as the change grows and drops below zero at the step where the screen changes. A different game of the same genre also looks different, which explains why similar-game experience did not help in Section 4.3.

4.6Learning a chain of games: no speed-up, and forgetting

Each of the previous results measures one aspect. To look at lifelong learning as a whole, we adopt the standard evaluation of continual learning (Lopez-Paz & Ranzato, 2017). The agent learns a chain of games one after another. After each game, a frozen copy of the agent is tested on every game in the chain, which yields a performance matrix. The matrices confirm the earlier findings and reveal something the earlier experiments could not see. Each game is learned to a moderate level: after one attempt reaches 0.8, the hidden-seed average is only 0.70, so reaching the threshold once is not the same as having learned the game. Forward transfer is around zero, and the cost of learning does not fall along the chain (games not learned within 8 attempts count as 9; with four runs, position cannot be separated from game difficulty).

The new finding is forgetting, with a concrete mechanism. The Snake skill contained import vision, but the shared library had no such module at the time, so the skill could not start and the model played by reading the screen, scoring 1.00. Later, while learning Chrome Dino, the agent wrote a new module called vision.py for Dino. From then on, the old Snake skill imported successfully and took over the game. It died 12 times per attempt and its score fell to 0.33. The Snake skill had not changed by a single character; code that another game had written into the shared library broke it. This is the mechanism of Section 4.4 seen from the other side of time: what is shared is perception code, and perception code does not generalise across games.

A caveat: the same code on the same seeds can vary from 0.56 to 1.00 per attempt, because game timing is not fully deterministic. With only 2 measurements per cell, forward transfer and forgetting smaller than about 0.15 cannot be distinguished from noise. The Snake case above is deterministic; the other numbers should be read as directions.

5Discussion: how far are we?

Capability a lifelong game agent needsStatusEvidence
Improve within a game from feedbackYes, if experience is written as code4.1
Organise its own memoryYes, within a single game's engineering loop4.2
Learn a game to a stable high levelPartly: about 0.70, and unstable4.6
Carry experience to the next gameA constant benefit that does not accumulate4.3
Store game rules independent of the screenNo; rules stay in notes4.4
Keep experience valid when the environment changesOnly if the screen is unchanged; decision knowledge is the exception4.5
Explore to discover changed rulesNo4.5
Learn faster over timeNo4.3, 4.6
Learn new games without forgetting old onesNo; shared code causes forgetting4.6

Of the three capabilities, the first two are within reach; the third breaks at a specific point. The agent's experience exists as perception code plus score records, and both are expressed in pixel coordinates. This accounts for every negative result. Transfer between similar games is negative because inherited perception code must first be repaired. The benefit stops growing because engineering lessons saturate after one or two games. Reskinning breaks everything. And rewriting shared perception code for a new game breaks the old ones.

The distance to a lifelong game agent is not that it cannot learn. It is that what it learns only holds in the pixels it has seen.

The shape of the gap is therefore clear. What is missing is a representation independent of appearance (objects, relative positions, speeds, and rules stated over them) together with a tendency to abstract at that level. The line thr = 2.2 * spd in the Dino skill and the note "steps in the danger zone equal width divided by speed" show that the model can write such rules. The Wolf3D exception shows that once such knowledge exists in a form that does not depend on appearance, it survives a rule change. The problem is that the agent never separates rules from perception code to store and reuse them on their own.

Relation to prior work. On twelve Unreal Engine games, OmniGameArena finds that a skill's gain on the original task does not predict its transfer to held-out variants; in one game the model with the largest original gain (+201%) transferred negatively to all three variants, consistent with our reskin result. On text games with unfamiliar rules, Learn2Play Bench finds that keeping complete records of actions and feedback works better than summarising experience into rules, and that human players try more varied strategies and repeat actions less than agents, which echoes the "stick with the champion, do not explore" behaviour we observe. In text environments, the memory mechanisms with evidence of cross-environment transfer are contrastive distillation of sub-task lessons from successful and failed trajectories (ExpeL, ReasoningBank) and memory consolidators trained on downstream task reward (Auto-Dreamer). Prompt-driven offline "sleep" consolidation has no evidence of task transfer so far. Work in which agents rewrite their own learning procedure, such as Hyperagents, shows that a learned learning procedure can speed up the start on a new domain, though the evidence remains limited. To our knowledge, no prior work has measured skill transfer between different games from pixels against a from-scratch control.

Next steps. The chain performance matrix can serve as a single yardstick for comparing agent designs: the diagonal measures learning, the upper right generalisation, the lower left forgetting, and the cost column whether learning speeds up. Once the yardstick is more precise (more measurements per cell, versioning of the shared library, and "learned" defined as two consecutive attempts above threshold), three content-neutral mechanisms can be tested in turn: regression-testing learned games before any change to shared code (aimed at forgetting); periodically laying out all games' skills and curves side by side and asking the agent for what they have in common (aimed at transfer); and finally letting the agent improve its own learning procedure with the matrix as the objective. Two further variables need testing: whether a stronger base model separates rules from perception on its own, and whether a stream of games with deeper shared structure and recurring variants rewards abstraction enough to make it worthwhile.

6Limitations

  • Small samples. Most conditions have one or two agents per cell, and two agents under identical conditions can differ by a factor of two. Each conclusion's direction holds across five to nine games or across most pairs; individual values are reliable to roughly ±0.15 to ±0.3.
  • One model. Whether a stronger model would abstract game rules on its own is the most direct untested variable.
  • Short lives. Six to ten attempts per game and at most six games in a row; several tasks hit the ceiling of 1.0, which compresses differences.
  • Scope of games. Pausable 2D and simple 3D browser games only. Real-time, multiplayer and long-horizon strategy games are out of scope.
  • Uninformative or thin evidence in places. The "points only while ducking" rung on Chrome Dino scored 0 on both sides; the robustness of decision knowledge was observed in Wolf3D only; the chain experiment has two chains with two runs each, and position is confounded with game difficulty.

Implementation details

  • Per-step decisions run with the model's reasoning off (about 1.2 s per step). Reflection after each attempt uses medium reasoning with a 48k-token output budget, retried at lower effort if reasoning exhausts the budget and returns an empty reply.
  • Skill programs run in a separate process with a 2-second limit per frame; on error or timeout, the model decides that step.
  • Notes are truncated at their limits; the shared library has no limit (a separate experiment capped all memory at 8,000 characters; see Section 4.3).
  • Control-feel changes are applied in the key-execution layer; rule changes are patches that generate separate local copies of the game; reskins transform the screenshot colours and leave game logic untouched.
  • In the chain experiment, learning stops when an attempt reaches the threshold or after the 8th attempt, and no reflection follows that attempt, so the version measured is the version that earned the score.
